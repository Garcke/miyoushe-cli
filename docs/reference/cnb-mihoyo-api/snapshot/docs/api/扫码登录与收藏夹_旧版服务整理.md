## 一、扫码登录(hk4e-sdk,无需账号凭据)

走的是"游戏扫码"通道(`hk4e-sdk.mihoyo.com`),生成二维码后由**已登录的米游社 App 扫码确认**,换回账号凭据。两步:取二维码 → 轮询状态。

### 1.1 获取二维码

```
GET https://hk4e-sdk.mihoyo.com/hk4e_cn/combo/panda/qrcode/fetch
    ?app_id=12
    &device={uuid4}
```

- `app_id=12`:实测返回 `app_name=绝区零, biz_key=nap_cn, bbs=true`(米游社扫码场景用此 id,来自旧代码验证过的取值)
- `device`:客户端自生成的 UUID,后续轮询必须带**同一个** device

**响应**(`retcode=0`):

```json
{"retcode": 0, "message": "OK",
 "data": {"url": "https://user.mihoyo.com/qr_code_in_game.html?app_id=12&ticket=...&expire=..."}}
```

- `data.url` 即二维码内容(生成二维码图片给用户扫)
- `ticket` 从 url 的 query 中提取,用于轮询
- `expire` 为绝对时间戳,但**实测 ticket 真实有效期只有约 2-3 分钟**(超时轮询返回 `rc=-106 二维码已过期`),建议轮询循环内做自动重新 fetch

### 1.2 轮询扫码状态

```
POST https://hk4e-sdk.mihoyo.com/hk4e_cn/combo/panda/qrcode/query
    ?app_id=12&device={同一个uuid}&ticket={ticket}
```

**状态机 `data.stat`**(2026-08-30 实测):

| stat | 含义 | data.payload |
|---|---|---|
| `Init` | 已创建、未扫码(实测轮询保持此值;旧代码记录的 `Created` 疑似已更名) | 无 |
| `Scanned` | 已扫码、待确认(旧代码路径推断,未实测) | 无 |
| `Confirmed` | 用户已确认 → **取凭据** | `payload.raw` |

异常:无效/过期 ticket → `retcode=-104 "系统请求失败，请返回重试"`(实测)。建议轮询间隔 1-2s,出现 -104 或长时间 Init 则重新 fetch。

### 1.3 凭据提取(Confirmed 之后)与 2026-08-30 二次实测修正 ⚠️

`data.payload.raw` 是 JSON 字符串,含三个字段:

```json
{"uid": "米游社UID", "mid": "账号mid", "token": "v2_ 前缀登录 token(152 字符)"}
```

**❗旧代码 `stoken = mid + token` 拼接规则已失效**(实测 2026-08-30):mid+token 拼接体和 token 原文两种形式都试过——

| 尝试 | 结果 |
|---|---|
| Cookie stoken = mid+token 拼接 | 宽松接口(userList/getUserFullInfo 等 11 条)rc=0,严格接口(chat/missions/binding/takumi 账号域)一律 `-100 登录失效/未登录` |
| Cookie stoken = token 原文(v2_ 前缀) | 同上 |
| `getTokenByGameToken` 交换(takumi/passport × bbsDS/passportDS × int/str aid × 有无 SDK 头 × JSON/表单/query 全变体) | `-3005 参数不合法` / 加 SDK 头后 `-5300 请升级应用版本` |
| `app/exchange` 按 HAR 真实 schema(src_token{token,token_type:1}+mid+dst_token_type:4) | `-100 登录状态失效`(schema 对,token 被拒) |
| 换用 HAR 可信设备头 + 新 token | 仍 `-100` —— 排除设备信任问题 |

**结论:该二维码是 hk4e-sdk 的"游戏登录码"(app_id=12,实测签发上下文为绝区零/nap_cn),产出的 token 是游戏侧会话凭据,在协议设计上就不产出完整 BBS stoken。** BBS 侧的 passport SDK(classes4 `PorteQRLoginManager`)只实现了**扫码方**协议(`scanQRLogin`/`confirmQRLogin`/`cancelQRLogin`,均需已有登录态),请求方协议(生成可产 BBS stoken 的二维码)在 Web 端(user.mihoyo.com)实现,SDK 内无对应接口。要拿到完整 BBS stoken,可走:①App 内密码/短信登录抓包;②逆向 Web 端 V2 QR 请求方协议(后续工作)。

**实测仍可用的部分**:该 game token 的登录态可通过约 11 条宽松接口(见 `tools/probe_results_qr.json`),足以做收藏夹 `userList`/`getUserPostListWithCollection`、用户信息等只读查询。

工具:[`tools/qr_login.py`](https://cnb.cool/NRD-Tech/Reverse_Project/-/blob/7afa9b30602cea79ce32b3ff70f7c8b352b3d825/mihoyo_bbs/tools/qr_login.py)(上游固定快照;生成二维码自动弹窗 + 过期自动刷新 + 轮询保存 `credentials_local.json`,该文件已加 .gitignore 严禁入库)。

## 二、收藏夹(painter 域,需登录 + DS)

### 2.1 用户收藏帖子列表

```
GET https://bbs-api.miyoushe.com/painter/api/userFavouritePostList
    ?aid={stuid}          # 即登录返回的 uid
    &offset=              # 分页游标,首页传空串
    &size=20              # 每页数量(旧代码固定 20)
    &game_uid={游戏UID}
    &game_region={区服}    # 如 cn_gf01
```

请求头:登录态组合(见 §三)+ `DS`(2026-08-30 注意:salt 已轮换,用 mys_ds_gen.py 生成)。

**响应结构**(旧代码消费路径):

```
data.list[]          # 收藏条目
  ├─ post            # 帖子摘要:post_id / game_id / subject / ...
  └─ vod_list        # 视频列表(列表页可能缺,需 getPostFull 补全,见 2.3)
data.is_last         # 是否最后一页
data.next_offset     # 下一页游标(传回 offset 参数)
```

分页循环:`offset=""` 起步 → 每页取 `next_offset` 继续,直到 `is_last=true` 或本页数量不足(旧 RAG 代码上限 50 页)。

**实测行为**(2026-08-30,无凭据调用):HTTP 200 + `retcode=1001 "权限不足"` → 接口本身可用,必须带有效登录 Cookie。完整登录态复现请参考 [米游社接口清单_DS闭环验证.md](米游社接口清单_DS闭环验证.md) 的头部组合。

### 2.2 前置:拿 game_uid / game_region

收藏夹按游戏角色过滤,角色列表来自(✅ 已在 2026-08-30 闭环清单中):

```
GET https://api-takumi.miyoushe.com/binding/api/getUserGameRolesByStoken?game_biz=hk4e_cn
Cookie: stuid=...; stoken=...; mid=...
→ data.list[] 中取 role_id(即 game_uid)和 region(如 cn_gf01),默认区服 cn_gf01
```

### 2.3 补全:vod_list / 帖子全文

```
GET https://bbs-api.miyoushe.com/post/api/getPostFull?post_id={post_id}
```

收藏列表条目缺 `vod_list` 时用此接口补全(✅ 已在闭环清单)。

## 四、old_api 值传递链与"有些接口不行"的完整实验(2026-08-30)

### 4.1 扫码成功后的值传递链(代码级)

```
routers/login.py POST /api/login/qrcode/status
  └─ services/mys_api.py query_qrcode_status(ticket, device_id)
       POST hk4e-sdk .../qrcode/query → data.stat == "Confirmed"
       └─ extract_credentials(raw)                          # services/mys_api.py:77
            stuid  ← raw.uid                                # 米游社 UID
            mid    ← raw.mid
            token  ← raw.token                              # v2_ 前缀,152 字符
            stoken ← mid + token  ←❌ 已失效的拼接规则        # services/mys_api.py:82
  └─ 返回 {status:"confirmed", credentials:{stuid, stoken, mid, token}}
       (调用方把这 4 个值传给业务接口)

业务接口侧 services/mys_api.py api_headers(stuid, stoken, mid):55
  ├─ Cookie: stuid={stuid};stoken={stoken};mid={mid};
  ├─ DS: gen_ds() ← DS_SALT="lX8m5VO5..."(2.102 时代盐,已死)  # :22,:27
  └─ 设备: 硬编码 DEVICE_ID/DEVICE_FP(:23,:24) ←⚠️ 与扫码时的随机 device 不是同一个
```

### 4.2 失败原因对照实验(三变体 × 四接口,实测)

| 变体 | roles(binding) | collection/userList(宽松对照) | chat/getChatList | getCookieAccountInfoBySToken |
|---|---|---|---|---|
| ① old_api 完全复刻(死盐+拼接体+老设备) | -100 登录失效 | **rc=0 ✅** | -100 登录失效 | -100 登录失效 |
| ② 当前盐(d64014...) + mid+token 拼接体 | -100 登录失效 | **rc=0 ✅** | -100 登录失效 | -100 登录失效 |

**结论:三种变体结果完全一致 → 失败与盐无关、与 stoken 拼接方式无关、与设备无关。唯一原因是这个二维码 token 是游戏侧凭据(hk4e app_id=12),权限等级只够"宽松接口";严格接口要求真正的 BBS stoken(密码/短信登录签发)。**

## 六、hoyolab 流(ma-cn-passport/web)✅ 产出完整 web 登录态(2026-08-30 实测闭环)

UIGF 文档区分了两种扫码:**qrcode_hk4e**(§一,Game Token,游戏侧凭据)与 **qrcode_hoyolab**(本节,BBS 登录态)。工具:[`tools/qr_login_hoyolab.py`](https://cnb.cool/NRD-Tech/Reverse_Project/-/blob/7afa9b30602cea79ce32b3ff70f7c8b352b3d825/mihoyo_bbs/tools/qr_login_hoyolab.py)(上游固定快照),凭据存 `credentials_local_hoyolab.json`(已 .gitignore)。

### 6.1 流程(全部实测通过)

```
1. POST https://passport-api.miyoushe.com/account/ma-cn-passport/web/createQRLogin
   头: x-rpc-app_id: bll8iq97cem8 + x-rpc-device_id(仅需这两个,-3001=缺头;无需 DS)
   → data.url(login-platform/mobile.html?...&token_types=4) + data.ticket
2. 展示二维码(App 扫码 → 确认)
3. POST https://passport-api.miyoushe.com/account/ma-cn-passport/web/queryQRLoginStatus
   body: {"ticket": ...}   → data.status: Created → Scanned → Confirmed(-3501 过期/-3505 取消)
4. Confirmed 后从该响应的 Set-Cookie 直接拿完整登录态(无需任何交换!)
   实测字段: ltoken_v2, cookie_token_v2, account_id(_v2), account_mid_v2, ltmid_v2, ltuid(_v2)
```

### 6.2 凭据能力实测(hoyolab cookie)

> ⚠️ 实测确认:**hoyolab 扫码测试账号(`<QR_TEST_ACCOUNT>`)与 HAR 主测试账号(`<HAR_TEST_ACCOUNT>`)是两个不同账号**。主账号经 SToken 路线
> (`getUserGameRolesByStoken`)已完整复现游戏账号信息:2 个绑定角色(原神 hk4e_cn/cn_gf01 + 绝区零 nap_cn/prod_gf_cn),
> 全字段(game_biz/region/game_uid/nickname/level/is_chosen/region_name/is_official)齐备;并用真实 game_uid/region
> 跑通收藏夹(5 条数据+翻页游标)——**old_api 整条 roles→favourite 业务链复活,无需任何额外参数**。
> hoyolab 账号 LToken 路线 rc=0 但绑定角色为 0(该账号未绑游戏,非接口问题)。

| 接口 | 组合 | 结果 |
|---|---|---|
| `/binding/api/getUserGameRolesByCookie`(roles,LToken 路线) | client_type=5 + DS2(4X 盐) | **rc=0 ✅** |
| `/painter/api/userFavouritePostList`(old_api 收藏夹,真实 game_uid/region) | client_type=2 + DS1 | **rc=0 ✅(5 条+翻页)** |
| §4.3 的 11 条宽松接口 | 同上 | ✅ |
| chat/missions/collection list/getPostDelConfigList/replyPermission/check release/notify settings/remained_times/genAuthKey/exchange | 任意组合 | ❌ 均需 **stoken** |

### 6.3 stoken 为什么拿不到(实验闭环)

createQRLogin 返回的 url 固定带 `token_types=4`(cookie_token);尝试 body `{token_types:[1,4]}`、`{token_types:1}`、query 变体,服务端**一律强制返回 token_types=4** → stoken 被安全设计排除在 web 扫码之外。stoken 只存在于 App 内部会话(即 HAR 抓包路径)。

### 6.4 对 old_api 的意义

- **断头链已接上**:roles 改走 `getUserGameRolesByCookie`(LToken),收藏夹 `userFavouritePostList` 直接用 hoyolab cookie——`old_api/services/mys_api.py` 只需把 Cookie 从 stoken 三件套换成 hoyolab cookie 串即可复活大半
- **仍不可达**:chat/任务/genAuthKey/exchange 等 stoken 专属接口,除非 App 内抓包
